Doesn't adding the input listener slow down editing?

Good question — performance is always a concern when you’re wiring up live editing. The short answer: an input listener itself doesn’t slow things down noticeably, because it only fires when the DOM changes. What can cause lag is the work you do inside that listener.

Here’s how to keep it snappy:

⚡ Performance Tips

  • Scope your cleanup narrowly: Instead of scanning the whole contenteditable div every time, just target the newly inserted node. For example, use MutationObserver to watch for added <span> elements and unwrap them immediately:

    js

    const observer = new MutationObserver(mutations => {
  mutations.forEach(mutation => {
    mutation.addedNodes.forEach(node => {
      if (node.nodeName === "SPAN") {
        node.replaceWith(...node.childNodes);
      }
    });
  });
});

observer.observe(editableDiv, { childList: true, subtree: true });

    This way you’re not looping through all spans on every keystroke.

  • Debounce heavy operations: If you do need to sanitize the whole content, debounce it (e.g., run after 100ms of inactivity). That avoids hammering the DOM on every single keypress.

  • Keep DOM ops minimal: Replacing nodes is cheap if you’re only touching the ones that matter. Avoid regex replacements on innerHTML every keystroke — that’s the slow path.

🚀 Practical Rule of Thumb

  • input listener with a small, focused sanitizer = fast enough for live editing.

  • Whole‑document regex cleanup on every keystroke = laggy.

  • MutationObserver = best balance, because it reacts only when the browser inserts unwanted spans.

The ... you saw in ...span.childNodes is JavaScript’s spread operator. It’s basically a way of “unpacking” an iterable (like an array or a NodeList) into individual items.

So in this line:

js

span.replaceWith(...span.childNodes);

what’s happening is:

  • span.childNodes is a NodeList of all the children inside that <span>.

  • The spread operator ... expands that NodeList into separate arguments.

  • replaceWith() then replaces the <span> itself with each of its children, effectively unwrapping the span.

Without the spread operator, you’d be passing the NodeList object itself, which replaceWith() doesn’t know how to handle. With ..., you’re saying “take each child node and insert it here.”

Quick analogy

Think of ... as opening a box and laying out all the items inside, instead of handing over the sealed box.

Example

js

const arr = [1, 2, 3];
console.log(...arr); // logs 1 2 3 separately

Same idea with DOM nodes: you’re unpacking them so they can be placed individually in the document.

Since you’re testing with larger content, this spread trick is actually quite efficient — it avoids rebuilding the whole innerHTML string and just unwraps spans in place.

Is this same as array walk?

Not quite the same as an array walk. Let me break it down:

🔹 Array Walk vs. Spread Operator

  • Array walk (like forEach, map, etc.) Iterates through each element and lets you run a function on it. Example:

    js

    [1,2,3].forEach(n => console.log(n));

    → prints each number one by one.

  • Spread operator (...) Doesn’t iterate with logic — it just expands the collection into individual items. Example:

    js

    const arr = [1,2,3];
console.log(...arr); // prints 1 2 3

    → no loop, just unpacking.

🔹 In Your Case

js

span.replaceWith(...span.childNodes);

  • span.childNodes is a NodeList (like [textNode1, textNode2]).

  • ...span.childNodes expands that list into separate arguments.

  • replaceWith() then replaces the <span> with each child node individually.

  • Result: the span disappears, but its children stay in place.

If you tried to “walk” the array with forEach, you’d have to manually insert each child back into the DOM. The spread operator is a shortcut that does it in one shot.

So: array walk = process each item with logic, spread = unpack items into arguments.

function wrapBlock(tagName, className) {
  setEditorFocus();
  const sel = window.getSelection();
  if (!sel.rangeCount) return;

  // Find the block-level ancestor of the cursor
  let node = sel.anchorNode;
  while (node && node.nodeType === Node.TEXT_NODE) {
    node = node.parentNode;
  }

  if (!node) return;

  // Only wrap if it's a block-level element (like P, DIV)
  const blockTags = ["P", "DIV"];
  if (blockTags.includes(node.tagName)) {
    const wrapper = document.createElement(tagName);
    if (className) wrapper.className = className;

    // Move the block’s children into the wrapper
    while (node.firstChild) {
      wrapper.appendChild(node.firstChild);
    }

    // Replace the block with the new wrapper
    node.replaceWith(wrapper);

    // Reset cursor inside the new wrapper
    const range = document.createRange();
    range.selectNodeContents(wrapper);
    range.collapse(true);
    sel.removeAllRanges();
    sel.addRange(range);
  }
}

  • Creates the new tag (<h1>, <h2>, etc.).

  • Moves all children into the new wrapper.

  • Replaces the old block with the new one.

  • Restores the cursor inside the new block so the editor can keep typing.

Yes, you can override that default behavior. By design, a contenteditable <div> will insert a new <div> when you press Enter, because the browser treats it as a block container. If you want Enter to produce <p> elements instead, you need to intercept the key event and insert your own block element.

Here’s a lightweight approach:

js

const editor = document.getElementById("basic-editor");

editor.addEventListener("keydown", e => {
  if (e.key === "Enter") {
    e.preventDefault(); // stop the browser from inserting <div>

    const sel = window.getSelection();
    if (!sel.rangeCount) return;

    const range = sel.getRangeAt(0);

    // create a new paragraph
    const p = document.createElement("p");
    p.appendChild(document.createElement("br")); // empty line

    // insert it after the current block
    range.insertNode(p);

    // move cursor inside the new paragraph
    range.setStart(p, 0);
    range.collapse(true);
    sel.removeAllRanges();
    sel.addRange(range);
  }
});

🔹 What this does

  • Prevents the browser’s default <div> insertion.

  • Creates a <p> element instead.

  • Inserts it at the caret position.

  • Moves the cursor inside the new <p> so typing continues naturally.

⚖️ Notes

  • If the caret is inside an existing block, this will split and insert a new <p> after it.

  • You can refine it to detect whether the current block is already a <p> and adjust accordingly.

  • Adding <br> inside the new <p> ensures it’s visible even when empty.
